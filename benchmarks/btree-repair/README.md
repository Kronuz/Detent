# Independent btree failure probes

The [copy evidence](../btree-isolated-copy-20261022.json) records compiler/platform qualification, cost ledgers and the remaining application failure. Compile each source against the selected header revision, using C++20. Use an isolated output directory and the workspace quiet protocol.

`copy_refusal.cc` copies three values and refuses the third mapped-value construction. On `2e93b45` it leaves one copied value live and exits 1; on `5aadde0` it releases the copied prefix and exits 0. This is an independent lifetime regression probe, not a general insertion-failure test.

`growth_refusal.cc` includes Detent's actual model, seeds a patch with a nested definition and permits one allocation before refusing another during compact-root growth. Compile with both the application's `include/` directory and the selected cpp-btree headers. On the recorded Linux profile it prints a 160-byte allocation followed by a refused 56-byte allocation, then reports one unreleased allocation on both revisions. Its exit code checks the attempted operation's refusal and retained map size; inspect the explicit allocation balance to detect this leak. LeakSanitizer alone did not report the block in this tiny probe, although the full publication sweep reports 3,120 bytes in 20 allocations.

The intended distinction is that the copy correction closes its targeted ownership defect while leaving an existing mutation defect visible. Neither probe claims that const-key mutation is defined behavior, that all allocation failures are covered, or that the production pin has changed.

`root_growth_refusal.cc` sweeps allocation refusal through compact-root growth with the real `SnapshotPatch` and nested `BoolDef` types. It covers short keys and legal maximum-length knob/group keys, before/middle/after insertion positions across one- and two-entry roots, preserved original values, and exact allocation balance after destruction. Compile with C++20, the chosen btree include root and Detent's `include/`; Linux ASan/UBSan is the qualification profile. The guarded candidate refuses 2, 7 and 12 positions respectively before its first successful insertion, with zero unreleased allocations in each attempt. This bounded probe does not qualify full-node splitting, rebalance or erasure.

`root_growth_cost.cc` repeats actual `SnapshotPatch` construction, one insertion and destruction 5,000 times for short/long keys and 1/2/4 seeded entries with three overrides. Compile the same source against both include roots with C++20, `-O3 -DNDEBUG` and Detent's `include/`. It reports process CPU and requested-allocation counters; seeding and destruction are inside the measured cycle. Instrumentation headers and allocator rounding are excluded from byte totals. The four-entry case can also traverse full-node paths. CPU comparisons require an accepted strict quiet run; allocation-only replay excludes the CPU fields.

`nonfull-replacement.patch` preserves the rejected direct leaf-replacement prototype against btree `fbeba8d`, solely for reproducing the [cost report](../btree-nonfull-replacement-20261022.json). It is excluded from product builds. Five guarded mutation pairs measure 329.422 versus 421.937 ms. Flat random insertion node allocations increase from 16,587 to 37,118, with the same retained node bytes. Node counters exclude ordinary string allocations. The separately extracted accounting fix does not need this patch.

The independent [nonfull accounting report](../btree-isolated-accounting-20261022.json) records the size-publication correction separately from the rejected replacement prototype. It includes all five paired samples and distinguishes node allocation counters from complete heap or RSS measurements.
