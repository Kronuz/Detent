# Detent architecture review: lifecycle scaling

**Date:** 2026-10-23. **Reviewed source:** `ceb2487` on `main`.
**Verdict:** **REJECT release-scale qualification.** The persistent authority and immutable local pages provide useful incremental mechanisms, but relay snapshot regeneration creates avoidable whole-state work and a bootstrap liveness risk. The operating envelope remains unqualified.

This review covers [release requirements](../RELEASE_PLAN.md), [capacity qualification](../CAPACITY_QUALIFICATION.md), [runtime capacity](../CAPACITY_RUNTIME.md), [container selection](../CONTAINER_SELECTION_ARCHITECTURE.md) and [btree risk](../BTREE_RELEASE_RISK.md). The calibration file is present at review completion; its capacity-forwarding and member-address ownership lessons apply. No earlier approval is inferred.

**Checked by:** Source-path tracing, independent reading of raw trial events, SHA-256 verification of all three raw files named by the committed report, and arithmetic checks. Complexity statements below follow the implementation; they are not measured attribution of elapsed time. No executable probe is produced.

## The three layers and the application reader

Let `N` be records in the relevant scope, `K` changed records, `P` reachable pages, `S` referenced segment packs, `D` encoded bytes, `H` retained history, and `R` readers or subscribers. Key length and override count remain separately bounded. Packs contain at most 1 MiB; pages are variable-length extents, capped at 64 KiB (`include/detent_local/paged_layout.hh:7`).

| Piece and owner | Work that grows | Memory and lifetime |
| --- | --- | --- |
| Authority: command validation and preparation | Request bytes, changed definitions, sorting/encoding within the bounded transaction | Queued/prepared commands and current application candidate coexist; limits must fund them together |
| Authority: committed state | AVL lookup/update is logarithmic in `N`; `K` mutations copy `O(K log N)` paths. Producer receipt copying also grows with its bounded receipt window | Three voters each own state. Immutable roots share unchanged nodes; old captures, changed definitions and reclamation queues retain additional memory |
| Authority: export and checkpoint | Full export/checkpoint traverses scoped records or complete state; incremental history encodes changed records | Captures pin roots. Checkpoint replacement overlaps the existing journal/image and requires reserved disk funding |
| Relay: upstream delivery and local publication | The same decode/build/recovery machinery as an agent, plus downstream representation construction | Durable mapped head, incoming decoded update, candidate packs, outgoing cache and retiring versions coexist per bundle |
| Relay: downstream fan-out | Encoding is shared; network bytes still grow with recipients. Retained edge lookup scans the configured history bound | Raw and compressed forms are both retained. Sessions share buffers but can keep distinct old versions alive |
| Agent: cold bootstrap | Decode, build all pages, validate, write, map, discover dependencies and validate mapped state | Decoded input, built output and mapped image can overlap. This is larger than steady mapped-reader memory |
| Agent: warm delta | Changed trie paths and definitions, plus whole-segment metadata and namespace passes described below | Shared unchanged mappings, new packs, candidate metadata and old leased generations coexist |
| Agent: recovery, collection and compaction | Cold recovery traverses the image. Collection depends on retained generations and files. Compaction scans all pages despite bounded output selection | Slow readers retain mappings/files. Sparse packs retain dead bytes until compaction and lease-safe collection |
| Application SDK: open and reads | Cold open validates the complete graph. Warm lookup follows the key path, with binary search over `S` segments at each page | Mappings plus segment metadata and validation scratch. Each reader process opens independently; pinned views extend generation lifetime |

Authority evidence: `src/detent_authority/persistent_map.hh:59`, `:92`, `:202`; application phases at `state.cc:1348`, `:1444`, `:1508`; shared capture at `export_capture.cc:5`; streaming checkpoint at `state.cc:1647`. A snapshot capture is cheap to create but can retain replaced nodes for its entire lifetime. Deferred cleanup bounds individual turns, not total retained bytes (`state.cc:815`). Actual AVL allocations use `new` and shared-pointer control blocks; logical `state_bytes` is not a requested-heap ceiling (`persistent_map.hh:59`, `deferred_values.hh:54`).

Local evidence: full construction at `src/detent_local/paged_snapshot_builder.cc:135`, `:258`; changed-path construction at `paged_delta_plan.cc:25`; cold/warm recovery selection at `generation.cc:351`. SDK lookup performs no whole-state traversal (`paged_read_state.cc:20`). Its cost still includes segment lookup, key bytes, override evaluation and cache misses; “mapped” does not mean constant-time or zero-memory.

Classic btree owns `Snapshot::knobs`, `SnapshotPatch::knobs`, `BoolDef::overrides` and CLI overrides (`include/detent/model.hh:27`, `:55`, `:82`; `include/detent/overrides.hh:22`). Managed authority keys use the separate AVL. Bool definitions still bring btree into authority construction and cleanup. A faster classic snapshot index cannot be credited with managed-key lookup or relay/agent improvements.

## Findings

### SC-1: Relay invalidation couples small updates to complete snapshots

**Blocking.** Every selected delta clears the cached full snapshot (`src/detent_distribution/update_cache.cc:37`). The host calls snapshot construction without waiting for a cold subscriber (`src/detent_relay/host.cc:279`). Construction reads the complete durable head; a new upstream stage cancels the in-flight snapshot (`bundle.cc:43`, `:152`). Installation accepts only the latest head (`bundle.cc:185`, `update_cache.cc:43`).

When an update leaves enough time for construction, even a one-key delta causes `O(N)` record work and `O(D)` outgoing snapshot work. Under frequent updates, construction can repeatedly restart and cold subscribers can remain busy. This is a source-established liveness risk; no starvation run is claimed. Growth with a completed rebuild after each fixed-size batch can accumulate quadratic total snapshot work. The supplied seed trial does not exercise this path during seeding.

Each stage constructs raw and compressed frames unconditionally (`src/detent_distribution/encoded_update.cc:111`, `:140`). Cache sizing therefore includes both representations, retained deltas, in-flight construction and buffers held by slow sessions. Encoding once per bundle avoids per-subscriber copies, but does not bound the number of distinct versions those subscribers retain.

### SC-2: Incremental publication still depends on all segment metadata

**Blocking qualification gap.** A small delta copies all `S` reachability rows in `sparse_plan_finalizer.cc:41` and `:113`. Warm validation seeds `S` removal rows and rereads namespace metadata (`paged_warm_validator.cc:225`). It records reachability for every target segment using binary searches (`:611`), giving an `O(S log S)` metadata path. Warm registry merge copies the mapping/ownership directory (`warm_registry_merge.cc:27`).

Publication also builds a complete reused-dependency vector (`paged_publication_artifacts.cc:38`). Recovery reopens ownership records and checks payload names for every referenced segment, including warm and same-state progress recovery (`generation.cc:463`). These checks protect durable identity and cannot simply be deleted. They establish `O(S)` filesystem work even when graph validation reuses unchanged subtrees.

Segment count can grow with update history at fixed `N`: new sparse packs preserve old packs with live records. Every new pack reserves a 1 MiB construction buffer, though its sealed file can be shorter (`paged_segment_builder.cc:49`, `:104`). A delta budget expressed only in changed keys misses metadata, allocation slack and pack fragmentation.

Compaction selects at most eight packs (`src/detent_delivery/coordinator.cc:318`), but relocation visits every page to find them (`src/detent_local/paged_trie_overlay.cc:168`, `:203`). Repeated small compactions can therefore cost `O(P)` apiece, plus segment lookups and publication metadata. Work-budget yielding controls latency per turn; it does not remove this total work. Qualification must vary `S`, fragmentation and held generations independently of `N`.

### SC-3: Cold construction/recovery has quadratic segment ordering and duplicate verification

**Blocking before larger-scale qualification.** Dependency discovery inserts each newly encountered segment into a sorted vector by moving its suffix (`paged_dependency_discovery.cc:132`). Candidate validation uses the same insertion pattern (`owned_segment_inputs.cc:70`, `:91`). These are worst-case `O(S²)` moves, and segment identities derive from hashes rather than traversal order (`paged_segment_builder.cc:38`). Sparse finalization also insertion-sorts added segments (`sparse_plan_finalizer.cc:85`); that term grows with the newly produced segment count.

Cold recovery hashes every discovered segment (`paged_dependency_discovery.cc:117`), then `GraphValidator` hashes all of them again (`paged_graph_validator.cc:201`) and traverses pages/definitions. The call chain is explicit at `generation.cc:370` and `:443`. Page checks provide additional integrity work. Cold opens remain necessarily proportional to admitted data under the current validation contract, but the duplicate passes and quadratic directory maintenance are avoidable candidates. Their timing contribution has not been measured.

Use one accounted segment-index/order mechanism with bounded incremental work and deterministic final ordering. For already collected candidate packs, a budgeted `O(S log S)` sort is sufficient. Online dependency discovery needs indexed lookup while gathering, followed by ordered emission. Preserve duplicate rejection and resource admission. Any hash-based index requires a reviewed adversarial-input policy; a standard ordered index avoids introducing that dependency. Removing repeated hashing requires an internal proof bound to the exact immutable mapping and ownership identity, with independent safety review.

### SC-4: Seed attribution and retained-state budgets remain missing

**Blocking.** There is no measured decomposition of the 104.338-second seed interval. The source does show bounded executor work and separate preparation/application passes (`service.cc:1638`, `:2407`), while idle turns use a timer (`:2491`). These are investigation entry points, not demonstrated causes. The separate seeding explorer owns that attribution.

Checkpoint work also grows with complete state, while its trigger depends on fixed log thresholds (`node.cc:467`; `state.cc:1663`). Repeated checkpoints during long growth can accumulate superlinear total bytes as the snapshot grows. Record checkpoint frequency and bytes before deciding whether this matters; the supplied timing is insufficient.

Capacity maxima must cover actual retained state, not just accepted logical records. In particular, authority path copies and retirement queues, relay snapshot versions, agent old/new mappings, and reader leases have different owners and lifetimes. No measured mapping from these populations to sustained accepted update rate or peak requested heap is available. The 5M profile is a configuration, not a supported operating point.

### SC-5: Btree safety remains an independent release blocker

**Blocking.** The production model still uses btree. Its documented full-node mutation/erase const-key and failure-cleanup risks remain in [BTREE_RELEASE_RISK.md](../BTREE_RELEASE_RISK.md); this audit does not independently reproduce or close them. Successful capacity trials do not test allocation failure or establish defined const-key mutation.

Complete the existing container decision against actual Detent values and cleanup paths. Standard ordered maps are a valid safety alternative if their full lifecycle costs fit the accepted budget. The hash snapshot prototype needs complete publication costs and collision policy before selection. Keep public C++ field-layout compatibility explicit. This decision remains separate from fixing the managed relay path.

## Validated architectural blueprint

Validation here means the diagnosis and ownership boundaries follow the source. Implementation and performance acceptance remain outstanding. Stop online-capacity feature planning until the scaling blockers are understood.

1. **Attribute seeding first.** Keep the existing explorer scoped to end-to-end preparation, consensus/storage and acknowledgment costs. Require exact source/binary identity, phase CPU, waits, accepted transactions, checkpoint bytes and counters for allocation/reclamation. Recheck the same small cardinality ladder after any fix. Preserve the existing durability contract.
2. **Implement one relay snapshot-lifecycle component.** Select a stable retained snapshot base plus bounded delta catch-up. Pin a durable immutable frontier `B`, finish its snapshot despite newer heads, and keep the contiguous history needed to advance from `B`. Continue sharing each encoded representation across sessions. Replace the base only when a successor snapshot and its required catch-up coverage are ready.
3. **Make the retention contract explicit.** Bound snapshot builders, encoded bytes, history bytes/edges, snapshot age and session leases. Reserve catch-up retention before admitting the build or subscriber. If coverage cannot be preserved within the budget, refuse new bootstrap admission or expire the affected session with an explicit restart requirement. Do not silently evict promised edges, serve an older cursor than a caller may accept, or block authority durability indefinitely. A successor base must be obtainable within the admitted write/retention envelope; sustained rates outside it require explicit backpressure.
4. **Keep session semantics in the same component.** Cache head, snapshot frontier and offered session target are distinct cursors. Adjust cache selection and session offers together (`src/detent_relay/sessions.cc:62`, `:99`); preserve authorization scope, policy epoch, lineage, revision monotonicity and acknowledgment binding. Existing sessions retain their selected immutable bytes. Restart, identity reset, missing history and resource refusal all have explicit outcomes. A source-level suggestion to relax only `snapshot.target == head` is insufficient.
5. **Reject a purely lazy rebuild as the sole remedy.** Building only when a subscriber asks saves idle encoding, but leaves cold latency proportional to the full dataset and still needs a pinned frontier plus catch-up retention under writes. Demand-triggered refresh can be a policy within the selected retained-base component; it is not a second snapshot mechanism.
6. **Bound the remaining local lifecycle before expansion.** Measure changed-definition work separately from segment-directory work, filesystem checks, compaction scans and cold validation. Remove quadratic segment ordering within the existing local ownership boundary. Keep current integrity checks until an equivalent proof mechanism is reviewed. Accept any remaining `O(S)` work only with measured `S`/fragmentation limits and an operating budget.

The relay component requires one independent code/logic review before landing, covering its concurrent update/bootstrap and resource-exhaustion cases. Review the complete component rather than individual commits. Keep generic container work with its library owner, preserve authority AVL ownership until extraction has its own evidence, and consult shared-library decisions before any consensus/journal/completion/reactor change.

## Required evidence and conditions

1. **SC-1:** Continuous writes during cold bootstrap must complete within the admitted retention envelope. Exercise slow/raw/compressed subscribers, history eviction, reconnect, cancellation, restart and identity changes. Count full snapshots, discarded bytes and simultaneous versions. A one-key update must not automatically rebuild the dataset.
2. **SC-2/SC-3:** Hold `N` fixed while increasing pack count and retained generations; then vary `N`. Record pages visited, definitions decoded, segment rows moved, segment bytes hashed, metadata syscalls, allocation requests and maximum executor turn. Include final cleanup and resource refusal. Verify exact complete state after every lifecycle.
3. **SC-4:** Publish repeated phase measurements and explicit latency/CPU/memory/disk budgets at the declared operating point. Separate sampled RSS, requested heap, mapped bytes and shared physical residency. Do not extrapolate dollars or power without a deployment model.
4. **SC-5:** Close actual-type mutation/failure cleanup or select and fully qualify the replacement. Keep the broader release plan's restore, composed-product, platform and fleet gates open.

**Final verdict:** REJECT release-scale qualification, with SC-1 through SC-5 open. This review authorizes diagnosis and the bounded relay remedy above; it does not approve an implementation or a larger supported ceiling.

**Not run:** Builds, tests, sanitizers, correctness probes, benchmarks, fuzzing, continuous-write starvation reproduction, multi-host/fleet trials, power-loss tests or independent btree failure reproduction. No code, dependency pin or external state is changed.
