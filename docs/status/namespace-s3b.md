- Blocked on (owner calls, none blocks the step):
  - **Linux private mapping and a rewritten verified page.** `test_testing_trusted_restart scrub-disk` aborted on Linux in CI with `std::invalid_argument: invalid paged local image` when it read between the rewrite and the scrub report: a clean `MAP_PRIVATE` page shares the page cache on Linux, so a write after the page was verified shows through, the page is still marked verified, and decoding it can throw instead of returning `SourceFailure`. This is the documented limit ("a page verified before it is damaged stays verified"), now observed to throw rather than only return a wrong value. The step narrows the window (the scrub reads the file and withdraws the bits when it reports) but cannot close it before the next scrub pass. Options: (a) leave as documented; (b) `ReadView` maps `invalid_argument` from a verified page to `SourceFailure`; (c) re-verify every page on every read (rejected: the first-touch design). I recommend (b) as a small follow-up; it touches user-visible read results, so it is yours.
  - **Every snapshot publication could recover without its prior.** A Replace with no repair pending (history lost) is a snapshot too, and its recovery is warm against a prior that may be damaged and not yet reported; it fails first touch and `settle_failure` fences the store (the restart then heals). Recovering every snapshot plan cold (as a repair does) closes that and, since a snapshot shares nothing with its base, does no more hashing than the warm path (which also walks the whole prior). It changes `test_testing_trusted_restart t5`'s "update over a damaged base is refused" and the recovery of every Replace, so I left it. Option: make `populate` and `capture` key on "plan built from a snapshot" instead of on `Repair`.
- Findings worth the architect's eye: (1) the collector's change (`tolerate_mismatch`) lets it delete a pack whose content differs from its owner record; everything else it proves is unchanged (owner record names this storage and segment, regular file of the owner's uid, mode, link count 1, length equals the record's, same inode before removal). (2) A collection requested while a reader still leases the damaged generation does nothing further; the next request (disk pressure, host) collects it. The coordinator requests one when a repair completes and does not retry. (3) The relay's own snapshot stage reads the damaged head and is not a repair trigger. (4) `request_repair` is coordinator memory, not durable: a restart during a pending repair finds the damage again at the first scrub pass.
- Design vs code:
  - D10.3 says the repair publishes "at the next build ordinal (D8)". The code publishes under random generation and segment ids (C2) at the selected cursor or later; S7 adds ordinal r + 1 to the id and the coordinator state here stays (A7).
  - D10.3 says a mismatch "fails that namespace alone". Today a store has one generation, so the code fails only the reads that reach a damaged page and nothing else; per-namespace isolation arrives with per-namespace generations (S7).
  - D10.2 says the scrub hashes "each pack against its owner record's checksum"; the code hashes the pack file through the store directory (pread, `F_NOCACHE` or `posix_fadvise`), not the agent's mapping, and reports a missing, resized or unreadable pack as damaged.
  - A7.4 names "an intent that skips the maintenance equality"; the code adds `PagedPlanIntent::Repair`, which also lets a repair go forward (a Replace at a later revision than the selected one), so a Replace that arrives while a repair is pending needs no second path.
  - The collector's proof of a candidate pack no longer includes the payload checksum for the packs it removes (see findings).
