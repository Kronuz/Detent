# Bounded authority application

Node owns one existing bounded committed range and advances at most one entry per service turn. Command entries decode and apply into one unpublished candidate across turns. Service splits one turn budget of 8 KiB of codec and row work, 16 metadata or override records, eight tree updates and 32 receipt or retirement records between application and publisher preparation. Each half reserves up to half its byte and retirement allowance for existing garbage before continuing active work. Standalone Node calls use the full budget. These are algorithmic work limits, not a strict CPU-time guarantee for tree comparisons, allocations or scheduling.

Later commands see earlier candidate changes, preserving the existing ordered batch semantics. Ordinary conflict and capacity results continue the batch. Exact command count, payload exhaustion and final index/term precede atomic publication of the state and receipts. Malformed later commands discard the candidate and fence through the original delivered range endpoint. Processed payloads retire individually, and the range receives one final Applied acknowledgement.

Repeated admission and drain calls do not advance application work. Storage and network scheduling continue while the slot is occupied. Checkpoint capture and snapshot activation require an empty slot; strong reads require the state to have reached their application boundary. CPU work resumes through an executor post so network and storage handlers can interleave without a mandatory timer delay per quantum. Pending waiter validation hashes the immutable original batch bytes incrementally before entry publication. Prepared publisher batches likewise hash their completed canonical bytes incrementally.

The [isolated 100k-knob comparison](../benchmarks/application-quanta-baseline.json) measured a maximum load service CPU turn of 73.234 ms before command quanta and 3.721 ms afterward. Total load CPU was 1198.843 versus 1189.425 ms. The synchronous disk fixture still had maximum wall turns of 73.437 versus 78.929 ms. These single samples demonstrate distributing work across turns; they do not establish production tails, native completion latency, or savings in total CPU or power.

Reproduce with `detent_authority_durable_bench NEW_DIRECTORY 100000 64`, using a fresh directory and no concurrent builds or tests. Maximum configured command, candidate disposal and reclamation costs remain qualification work for the complete readiness component.

Nine native checks passed in 78.35 seconds and nine ASan/UBSan checks in 83.01 seconds on macOS, including state equivalence, malformed final commands, multi-entry failure fencing, held network output, grouped-entry atomic visibility, service authentication and three-process pressure/failover with drained-credit assertions. All nine Linux checks passed in 38.89 seconds with native completion storage after the single-hash optimization and stronger drained-credit assertions. These gates qualify this application increment, not the complete authority readiness or fleet stages.

The [large-command baseline](../benchmarks/command-work-baseline.json) records three fresh-store service runs with a legal 257303-byte transaction containing 128 mutations and 31 overrides per definition. The longest owner CPU turns were 11.479, 10.613 and 10.108 ms. Five synchronous State samples also cover unchanged definitions, conflicting CAS, capacity rejection, duplicate retries, full producer receipt histories and a definition near its byte limit. Setup is outside the timed State operations; cleanup measurements cover persistent-tree collection and do not include every decoded-command destructor.

Finer command continuations are being implemented within readiness. The accepted Architect blueprint budgets decoding, canonical hashing, comparison, capacity accounting, tree changes, receipt work and disposal on the owning executor, sharing one budget across phase changes. A validated capability binds the decoded command, canonical digest, immutable profile and measured definition sizes. Integration must retain exact entry exhaustion and atomic publication; the baseline is evidence of the remaining pause, not a completed performance improvement.

The finer decoder and command application now feed the Node batch candidate. Native state and Node checks pass on macOS and Linux, and the isolated state histories pass ASan/UBSan on macOS. The full authority sanitizer and service gates are being rerun after integration. Native and ASan/UBSan state tests compare each completed result and checkpoint byte for byte with the synchronous implementation, while checking that the public source remains unchanged at every yield. The histories cover maximum override counts, unchanged definitions, conflicting CAS, sequence gaps, retained and evicted retries, a full receipt window, session closure and reopening, and incremental abandonment. Canonical hashing reuses validated input bytes; cached definition sizes avoid re-encoding for capacity accounting, and transferred override roots avoid whole-definition copies. Deferred payload retirement retains its original byte charge until the final row is cleared. Failed Node entries keep their partial decoder and candidate until bounded disposal drains, then retire remaining payloads one per turn. Shutdown drains pending application and reclamation work as well as original IO. Whole-turn CPU and memory measurements and the broader integration gates still require qualification.

Publisher batch selection accounts for the complete canonical header, derived from the codec. DTABAT02 has a 96-byte prefix, including the replicated semantic profile, followed by eight length bytes per command. The previous 16-byte accounting undercounted batches by 80 bytes and could select a group that the final encoder rejected at the byte limit. State tests pin the framing size, exact-cap acceptance and one-byte-over-cap rejection.

The resumable publisher codec now orders borrowed mutation references and emits individual override rows without copying definitions. A batch builder reserves one bounded buffer, copies one encoded command incrementally, patches the final count and hashes the exact completed bytes in bounded steps. Encoded-command and prepared-proposal capabilities invalidate on move. Native codec and Node tests cover byte identity, carryover after a batch fails to fit, exact-cap boundaries, the 64-command limit, foreign profiles, and repeated Busy or Pressure admissions. Node allocates waiter bookkeeping before admission and submits retained bytes; its synchronous proposal API drives the same machinery for compatibility. Service now prepares one batch at a time and carries one command that did not fit into the next batch, preserving queue order. It retains exact prepared bytes across Busy and Pressure rather than returning tasks for re-encoding. Completed command payloads retire through a preallocated FIFO while retaining their original admission charges. Native service smoke tests pass; maximum-command, deadline, shutdown, sanitizer and multi-process qualification are in progress.

Health exposes `retired_state_values`, `retired_state_value_bytes`, `retired_publisher_tasks` and `retired_publisher_bytes`. These count queued value ownership and retained codec or admission charges, not total physical heap allocation. The original charge remains until the final disposal step. RSS and allocator measurements are needed to quantify the added metadata and separate control blocks.

The accepted read-response blueprint keeps one owner-local frozen state capture through counting, encoding and retirement. Other completed quorum reads retain only their admitted task and verified boundary. An incremental first pass counts the exact JSON, including the authority envelope, before reply quota and body capacity are reserved; a second pass emits directly from the immutable definitions. The counted reservation must transfer to HTTP egress and remain charged until original write or disconnect settlement. This removes the per-definition DOM and the final envelope copy, but adds a second traversal; total CPU and peak retained memory must be measured rather than inferred. Snapshot activation can leave the read slot as the last owner of old state arenas, so cancellation, completion and shutdown must explicitly retire and budget-collect those roots before releasing the capture. Frontend scheduling must share its existing allocation fairly between publishing, reading and reclamation. Service now uses this slot and transfers the counted reservation to egress. Native tests compare exact JSON with the independent DOM oracle, exercise a legal 32768-override read across state replacement, and drain the old capture with one retirement row per quantum. A deferred-writer test holds the first original write and verifies that the next counted read retains one capture, reserves no body buffer under quota pressure, and proceeds with the same response after settlement. The read codec, Service and both Node storage modes also pass macOS ASan/UBSan and native Linux tests. Native FreeBSD gates also pass, and subsequent Service tests cover mixed read/write progress and deadline cancellation. The cluster fixture holds a counted read across actual follower snapshot activation and explicitly collects the old arena. Production transport overlap and the terminal gates in [Authority readiness](AUTHORITY_READINESS.md) remain open.

Read submission allocates its local waiter before consensus acceptance. Busy, Pressure, fencing and exceptions release that tentative waiter; an accepted read keeps its completion owner without a later allocation. Repeated Busy submissions with the same local request ID test that rollback leaves admission reusable.

The [read-response baseline](../benchmarks/read-response-baseline.json) measures a fresh durable Service with 128 knobs, 256 overrides per knob and five reads before resumable read integration. Each response is 2029728 bytes; read wall times range from 17.422 to 24.411 ms. The whole-workload owner CPU maximum is 15.626 ms and process peak RSS is 44892160 bytes. The owner histogram includes setup writes and ordinary reclamation, but is sampled before Service destruction and excludes final live State/Core teardown; these are baseline measurements, not a qualified before/after improvement.

Three serial fresh-store [measurement pairs](../benchmarks/read-response-measurements.json) compare synchronous serialization with the resumable Service. The owner CPU maximum falls from 14.670–15.675 ms to 0.262–0.277 ms, and process peak RSS falls from 42037248–46559232 bytes to 25882624–27238400 bytes. The tradeoff remains measurable: normal large-read wall time rises from 15.046–23.845 ms to 113.120–122.480 ms, and the whole-workload owner CPU sum rises from 0.502–0.504 seconds to 0.559–0.571 seconds. These sums are sampled before Service destruction and exclude final live State/Core teardown and other process threads and cannot establish a power or dollar saving. Node runs first; unused allocation is returned to frontend work, and an idle publisher no longer consumes alternating read turns. An additional legal escaping workload emits 9566368-byte replies, measures a 0.265 ms owner CPU maximum and 35094528-byte peak RSS, and drains all capture and retirement counters.
