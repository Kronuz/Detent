## CL-2: one ownership protocol

Today, file-only `acquire_owner(bool)` and directory-only `acquire_directory_owner()` lock different inodes and can both succeed on one directory. Treat mixed legacy owners as unsafe. A process taking both locks excludes either legacy mode, but a file-only old process and a directory-only old process still do not exclude each other. During rollout, any remaining file-only Detent writer still fails to exclude a directory-only strata writer. Migrate strata's mutable storage owners to `both` as well.

Use one canonical `acquire_owner(OwnerLockOptions)` implementation. Take the directory lock first, then `owner.lock`, and release in reverse. Preserve Detent's explicit exclusive-create versus existing-open policy, zero-length 0600 file and journal bootstrap accounting. Carry the selected protocol through Journal-owned locks as well as direct `StorageSession` calls. Retain ownership through outstanding original completions. Unsupported directory locking fails closed; there is no silent file-only fallback. This can reject a filesystem whose file lock worked but whose directory lock does not, so qualify that capability before deployment.

The old bool and directory entry points remain source-compatible forwarding presets during deprecation. Do not silently make the old directory-only call create a file. Strata needs an explicit owner-file bootstrap policy for existing directories. Unify EINTR handling and unsupported/busy errors, unwind partial acquisitions and descriptor state on failure, and avoid recursive base-IO compatibility forwarding. Test IO must model supported exclusion or report an unsupported capability, never claim success with a no-op owner lock.

Before either consumer changes its production protocol, test every `file/directory/both` pairing with separate processes, in both first-holder orders, through old and new APIs and through shared and distinct IO objects. The legacy file/directory pairing remains an unsafe control; every pairing involving `both` must exclude the competing owner. Reacquisition through one IO must not create independently releasable aliases. Internal acquisition order always stays directory then file. Include partial failure, EINTR, unsupported locks, create/recover, owner lifetime through IO completion and existing symlink/trust refusals on macOS, Linux and FreeBSD. Keep directories under one operational ownership protocol until the migration is qualified; this document alone changes no deployed exclusion.

The audit reviewed published application main, so its CL-17/18 observations do not include these isolated source candidates.

The HTTP terminal fixture distinguishes zero live domain work from retained weak-registration storage. After domain abandonment, the Reactor can retain an expired `allocate_shared` control block until another registration prunes it or `abort_all()` releases the registry. Both boundaries are checked, with exact allocation conservation after registry release. Immediate unregister would be a separate Reactor lifecycle change, not another accounting engine.

## Additional audit inputs

1. Detent's three private HTTP response paths and flat MessagePack codec are being consolidated into the existing HTTP and MessagePack libraries. The MessagePack output adapter delegates to the bundled packer; no second encoding engine remains in that candidate.
2. `persistent_map.hh` is still an extraction candidate. Immutable structural sharing and budgeted reclamation require their own boundary; the mutable cpp-btree const-key and exception-safety findings remain release gates.
3. Detent uses Kronuz/sha256 in rollout hashing, protocol digests and local images. No `EVP_Digest` bypass is present in its `src/` or `include/`. The global `SHA256` name still collides with OpenSSL and creates include-order workarounds; the audit's canonical namespaced/hardware-dispatch work should resolve that without changing digest bytes.
4. Keep completion's storage-owner lock, mapped-generation leases and CLI PID locks distinct by protected object and lifetime. Likewise, an IO completion executor and a reactor event loop need a shared scheduling plan before either is replaced. Similar names alone do not establish interchangeable ownership.
